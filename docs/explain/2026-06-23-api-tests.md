# 変更解説: CRUD API の自動テスト基盤

## 全体像

children / growth / growthStandards の CRUD API に自動テストを追加した（チケット #45）。**本物の PostgreSQL を使う結合テスト**で、`Vitest`（ランナー）＋ `Fastify.inject()`（HTTPを実ネットワーク無しで叩く）＋ `@testcontainers/postgresql`（テスト用 DB を自動起動）の3点構成。

テスト1回の流れ:

```
npm test
  → globalSetup: PostgreSQLコンテナ起動 → migrate → seed（1回だけ）
  → 各テスト: buildApp() で組んだ Fastify を app.inject() で叩く
  → teardown: コンテナ停止
```

## 変更ファイル一覧

| ファイル | 変更内容 |
|----------|----------|
| src/app.ts | `buildApp()` を新設（listen と分離） |
| src/server.ts | `buildApp()` を呼んで listen するだけに |
| vitest.config.ts | テスト設定（globalSetup / setup / 直列実行） |
| test/support/globalSetup.ts | DBコンテナ起動・migrate・seed（全体で1回） |
| test/support/setup.ts | 各ワーカーの環境変数設定 |
| test/support/helpers.ts | テストデータ生成（別ユーザーの子） |
| test/integration/*.test.ts | 実テスト3ファイル |
| test/tsconfig.json | テスト用の型チェック設定 |
| package.json | vitest / testcontainers 追加、`test` スクリプト |

## 詳細解説

### 1. src/app.ts — テストから叩けるように「組み立て」と「起動」を分離

リファクタ前は `server.ts` が「Fastify を組み立てて **その場で listen**」していた。テストでは実際にポートを開かず `inject()` で叩きたいので、**組み立てだけ**する関数を切り出した。

```ts
export function buildApp(options: { logger?: boolean } = {}): FastifyInstance {
  const fastify = Fastify({ logger: options.logger ?? true });
  registerAuth(fastify);
  fastify.get("/", ...);          // ヘルスチェック
  fastify.register(childrenRoutes, { prefix: "/children" });
  // ...ルート登録...
  return fastify;                 // listen はしない
}
```

`listen()` を含めないのがポイント。テストは `buildApp({ logger: false })` で静かなインスタンスを得て `inject()` する。

### 2. src/server.ts — 本番は buildApp して listen するだけ

```ts
const fastify = buildApp({ logger: true });
const start = async () => { await fastify.listen({ port, host: "0.0.0.0" }); };
start();
```

組み立ては app.ts に任せ、server.ts は「起動」だけの責務になった。

### 3. vitest.config.ts — テストの動かし方を指定

```ts
test: {
  globalSetup: ["./test/support/globalSetup.ts"], // 全体で1回だけ走る準備
  setupFiles: ["./test/support/setup.ts"],         // 各ワーカーで毎回走る準備
  fileParallelism: false,  // 1つのDBを共有するのでファイル並列を無効化
  hookTimeout: 120000,     // コンテナ起動は遅いのでタイムアウトを延長
}
```

`globalSetup` と `setupFiles` の違いが重要:
- **globalSetup**: テスト全体の前後で **1回だけ**。重い準備（コンテナ起動）に使う。
- **setupFiles**: 各テストワーカー（プロセス）で **毎回**。環境変数の設定などに使う。

`fileParallelism: false` … 3つのテストファイルが同じ1つのDBを使うため、同時に走るとデータが干渉する。直列実行にして競合を防ぐ。

### 4. test/support/globalSetup.ts — 本物の DB を立ててマイグレーション

テスト全体の前に1回だけ実行。`@testcontainers/postgresql` で **使い捨ての PostgreSQL** を起動し、実マイグレーションと seed を流す。

```ts
export async function setup(project: TestProject) {
  container = await new PostgreSqlContainer("postgres:16").start(); // DBコンテナ起動
  const databaseUrl = container.getConnectionUri();                 // 接続先（ポートは毎回ランダム）

  const env = { ...process.env, DATABASE_URL: databaseUrl };
  execSync("npx prisma migrate deploy", { env });   // テーブル作成
  execSync("npx tsx prisma/seed.ts", { env });      // 発育曲線マスタ等を投入

  project.provide("databaseUrl", databaseUrl);      // 接続先を各ワーカーへ渡す
}

export async function teardown() {
  await container?.stop();  // 終わったらコンテナ破棄
}
```

ポイント:
- **testcontainers**: テスト用に Docker コンテナを起動・破棄するライブラリ。モックでなく**実際の PostgreSQL** に対して検証できる。
- ポートは毎回ランダムなので、接続先は固定で書けない。`provide()` で各テストワーカーに渡す（vitest 4 では `project.provide`）。
- `provide` した値の型は、ファイル末尾の `declare module "vitest"` で `ProvidedContext` に登録して型安全にしている。

### 5. test/support/setup.ts — prisma が DB を掴む前に接続先を設定

各テストワーカーで、テスト本体の import より前に実行される。

```ts
process.env.DATABASE_URL = inject("databaseUrl"); // globalSetup が provide した接続先
process.env.AUTH_MODE = "dummy";                  // 認証はダミーで通す
```

**なぜ import より前が重要か**: `src/plugins/prisma.ts` は import された瞬間に `process.env.DATABASE_URL` を読んで接続先を確定する。テスト本体が prisma を import する前に、ここで接続先（コンテナのURL）を入れておく必要がある。setupFiles はテスト本体より先に走るので、ここで設定すれば間に合う。

### 6. test/support/helpers.ts — 所有権テスト用のデータ生成

「他人の子は 404」を検証するため、ダミーユーザーとは**別のユーザー＋その子**を直接 DB に作る関数。

```ts
export async function createOtherUsersChild(): Promise<number> {
  const user = await prisma.user.create({ data: { cognitoSub: unique, ... } });
  const child = await prisma.child.create({ data: { userId: user.id, ... } });
  return child.id;
}
```

API（dummy認証）からは常に「自分（ダミーユーザー）」として叩くので、他人のデータは prisma で直接用意するしかない。これを使って「他人の childId を叩く → 404」を確認する。

### 7. test/integration/*.test.ts — 実テスト

3ファイル共通の形:

```ts
beforeAll(async () => { app = buildApp({ logger: false }); await app.ready(); });
afterAll(async () => { await app.close(); await prisma.$disconnect(); });
beforeEach(async () => { await prisma.child.deleteMany(); }); // 毎テスト前にデータ初期化

it("POST /children → 201", async () => {
  const res = await app.inject({ method: "POST", url: "/children", payload: {...} });
  expect(res.statusCode).toBe(201);
  expect(res.json()).toMatchObject({ name: "...", gender: "..." });
});
```

ポイント:
- **`app.inject()`**: 実際の HTTP サーバを立てず、Fastify 内部にリクエストを流し込む仕組み。速くて後片付け不要。
- **`beforeEach` で `deleteMany()`**: テスト間でデータが残らないよう、毎回 children を消す（cascade で growth 等も消える）。マスタ（growth_standards）とユーザーは残す。
- **検証内容**: 正常系 CRUD、recordedAt 昇順、バリデーション400（両方なし/負値/不正日付）、404（不存在・他人の子・別の子経由）。所有権（他人のデータは触れない）も網羅。

### 8. test/tsconfig.json — テストの型チェックを通す

テストファイルは本体の `tsconfig.json`（`src/**` のみ）の対象外なので、IDE が `vitest` 型を解決できずエラーになる。テスト専用の設定で解決する。

```json
{
  "extends": "../tsconfig.json",
  "compilerOptions": { "types": ["node", "vitest/globals"] },
  "include": ["**/*.ts", "../src/**/*.ts", "../generated/**/*.ts"]
}
```

本体の typecheck（`npm run typecheck` = src のみ）は変えていないので、**コンテナ側の型チェックは vitest 非依存のまま**。テストの型だけこの設定でカバーする。

---

## まとめ

- **テスト容易性のための最小リファクタ**（buildApp 抽出）＋ **本物のDBを使う結合テスト**という、実務で一般的な構成。
- `globalSetup`（重い準備を1回）と `setupFiles`（各ワーカーの設定）の役割分担、`inject()` での高速HTTP検証、testcontainers での実DB検証が肝。
- 構成は `test/integration/`（実テスト）と `test/support/`（基盤）に分離して見通しを良くしている。
