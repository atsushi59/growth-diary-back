# 変更解説: CRUD API の自動テスト基盤

## 全体像

children / growth / growthStandards の CRUD API に自動テストを追加した（チケット #45）。**本物の DynamoDB(DynamoDB Local) を使う結合テスト**で、`Vitest`（ランナー）＋ `Fastify.inject()`（HTTPを実ネットワーク無しで叩く）＋ `testcontainers`（テスト用 DB を自動起動）の3点構成。

> 当初は Prisma/PostgreSQL ベースだったが、本体を DynamoDB へ移行したのに合わせてテストも DynamoDB Local 版に書き換えた。

テスト1回の流れ:

```
npm test
  → globalSetup: DynamoDB Localコンテナ起動 → createTables → seed（1回だけ）
  → 各テスト: buildApp() で組んだ Fastify を app.inject() で叩く
  → teardown: コンテナ停止
```

## 変更ファイル一覧

| ファイル | 変更内容 |
|----------|----------|
| src/app.ts | `buildApp()`（listen と分離） |
| src/server.ts / src/lambda.ts | `buildApp()` を呼ぶだけに統一（ローカル/Lambda 両対応） |
| vitest.config.ts | テスト設定（globalSetup / setup / 直列実行） |
| test/support/globalSetup.ts | DynamoDB Local 起動・createTables・seed（全体で1回） |
| test/support/setup.ts | 各ワーカーの環境変数設定（endpoint・AWS認証） |
| test/support/helpers.ts | テストデータ生成＋テーブル後始末 |
| test/integration/*.test.ts | 実テスト3ファイル |
| test/tsconfig.json | テスト用の型チェック設定 |
| package.json | vitest / testcontainers 追加、`test` スクリプト |

## 詳細解説

### 1. src/app.ts — テストから叩けるように「組み立て」と「起動」を分離

テストでは実際にポートを開かず `inject()` で叩きたいので、Fastify を**組み立てるだけ**の関数を切り出した。

```ts
export function buildApp(options: { logger?: boolean } = {}): FastifyInstance {
  const fastify = Fastify({ logger: options.logger ?? true });
  registerAuth(fastify);
  fastify.get("/health", ...);
  fastify.register(childrenRoutes, { prefix: "/children" });
  // ...ルート登録...
  return fastify;                 // listen はしない
}
```

`server.ts`（ローカル常駐）も `lambda.ts`（Lambda）も、この `buildApp()` を使う。テストは `buildApp({ logger: false })` で静かなインスタンスを得て `inject()` する。

### 2. vitest.config.ts — テストの動かし方を指定

```ts
test: {
  globalSetup: ["./test/support/globalSetup.ts"], // 全体で1回だけ走る準備
  setupFiles: ["./test/support/setup.ts"],         // 各ワーカーで毎回走る準備
  fileParallelism: false,  // 1つのDBを共有するのでファイル並列を無効化
  hookTimeout: 120000,     // コンテナ起動は遅いのでタイムアウトを延長
}
```

- **globalSetup**: テスト全体の前後で **1回だけ**。重い準備（コンテナ起動）に使う。
- **setupFiles**: 各テストワーカー（プロセス）で **毎回**。環境変数の設定などに使う。
- `fileParallelism: false` … 3ファイルが同じ1つのDBを使うため、直列実行にして競合を防ぐ。

### 3. test/support/globalSetup.ts — DynamoDB Local を立ててテーブル作成

テスト全体の前に1回だけ実行。`testcontainers` の `GenericContainer` で **使い捨ての DynamoDB Local** を起動し、テーブル作成と seed を流す。

```ts
export async function setup(project: TestProject) {
  container = await new GenericContainer("amazon/dynamodb-local:latest")
    .withExposedPorts(8000)
    .withCommand(["-jar", "DynamoDBLocal.jar", "-inMemory", "-sharedDb"])
    .withWaitStrategy(Wait.forListeningPorts())
    .start();
  const endpoint = `http://${container.getHost()}:${container.getMappedPort(8000)}`;

  const env = { ...process.env, DYNAMODB_ENDPOINT: endpoint, AWS_REGION: "...", /* dummy creds */ };
  execSync("npx tsx scripts/createTables.ts", { env }); // 4テーブル作成
  execSync("npx tsx scripts/seed.ts", { env });         // 発育曲線マスタ等を投入

  project.provide("dynamodbEndpoint", endpoint);        // 接続先を各ワーカーへ渡す
}
```

ポイント:
- **testcontainers**: テスト用に Docker コンテナを起動・破棄するライブラリ。モックでなく**実際の DynamoDB Local** に対して検証できる（PostgreSQL モジュールと違い DynamoDB は公式モジュールが無いので汎用の `GenericContainer` を使う）。
- ポートは毎回ランダムなので、接続先(endpoint)を `provide()` で各ワーカーに渡す（vitest 4 では `project.provide`）。
- DynamoDB SDK は region と credentials を要求するので、ローカルでもダミー値を渡す。

### 4. test/support/setup.ts — DynamoDB クライアントが掴む前に接続先を設定

各テストワーカーで、テスト本体の import より前に実行される。

```ts
process.env.DYNAMODB_ENDPOINT = inject("dynamodbEndpoint"); // globalSetup が provide した接続先
process.env.AWS_REGION = "ap-northeast-1";
process.env.AWS_ACCESS_KEY_ID = "dummy"; // DynamoDB Local 用ダミー
process.env.AWS_SECRET_ACCESS_KEY = "dummy";
process.env.AUTH_MODE = "dummy";          // 認証はダミーで通す
```

**なぜ import より前が重要か**: `src/plugins/dynamodb.ts` は import された瞬間に `DYNAMODB_ENDPOINT` を読んで接続先を確定する。テスト本体がそれを import する前に、ここで接続先（コンテナの endpoint）を入れておく必要がある。setupFiles はテスト本体より先に走るので間に合う。

### 5. test/support/helpers.ts — 所有権テスト用データ生成＋後始末

**他人の子の生成**: 「他人の子は 404」を検証するため、ダミーユーザーとは別のユーザー＋その子を repository 経由で直接作る。

```ts
export async function createOtherUsersChild(): Promise<string> {
  await upsertUserByCognitoSub({ cognitoSub, name, email });   // 別ユーザー
  const child = await createChild({ userId: cognitoSub, ... }); // その子
  return child.id;
}
```

**テーブル後始末**: DynamoDB には「全削除」が無いので、Scan で全アイテムを集めて BatchWrite で消す。children と growth を毎テスト前にクリアする。

```ts
export async function clearChildrenAndGrowth() {
  await clearTable(TABLES.children, ["userId", "id"]); // Scan → BatchWrite Delete
  await clearTable(TABLES.growth, ["childId", "id"]);
}
```

### 6. test/integration/*.test.ts — 実テスト

3ファイル共通の形:

```ts
beforeAll(async () => { app = buildApp({ logger: false }); await app.ready(); });
afterAll(async () => { await app.close(); });           // DynamoDB は disconnect 不要
beforeEach(async () => { await clearChildrenAndGrowth(); }); // 毎テスト前にデータ初期化

it("POST /children → 201", async () => {
  const res = await app.inject({ method: "POST", url: "/children", payload: {...} });
  expect(res.statusCode).toBe(201);
  expect(res.json().id).toBeTypeOf("string");  // id は UUID 文字列
});
```

ポイント:
- **`app.inject()`**: 実際の HTTP サーバを立てず、Fastify 内部にリクエストを流し込む仕組み。速くて後片付け不要。
- **`beforeEach` で `clearChildrenAndGrowth()`**: テスト間でデータが残らないよう、毎回 children/growth を消す。マスタ（growth_standards）とユーザーは残す。
- **id は UUID 文字列**（DynamoDB は自動採番が無いため）。検証も `toBeTypeOf("string")`。
- **検証内容**: 正常系 CRUD、recordedAt 昇順、バリデーション400、404（不存在・他人の子・別の子経由）。所有権も網羅。

### 7. test/tsconfig.json — テストの型チェックを通す

テストファイルは本体の `tsconfig.json`（`src/**` のみ）の対象外なので、`vitest` 型を解決できずエラーになる。テスト専用設定で解決する。

```json
{
  "extends": "../tsconfig.json",
  "compilerOptions": { "types": ["node", "vitest/globals"] },
  "include": ["**/*.ts", "../src/**/*.ts"]
}
```

本体の typecheck（`npm run typecheck` = src のみ）は変えていないので、テストの型だけこの設定でカバーする。

---

## まとめ

- **テスト容易性のための最小リファクタ**（buildApp 抽出）＋ **本物のDB(DynamoDB Local)を使う結合テスト**という、実務で一般的な構成。
- `globalSetup`（重い準備を1回）と `setupFiles`（各ワーカーの設定）の役割分担、`inject()` での高速HTTP検証、testcontainers での実DB検証が肝。
- 構成は `test/integration/`（実テスト）と `test/support/`（基盤）に分離して見通しを良くしている。
